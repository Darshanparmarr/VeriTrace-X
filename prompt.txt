# MASTER BUILD PROMPT — VeriTrace-X

## 1. Your Role

Act as a senior full-stack engineer, AI/ML engineer, UI/UX designer, software architect, and DevOps engineer.

Build **VeriTrace-X**, a complete, modern, production-minded web application for explainable AI-based supply-chain fraud detection and blockchain-based traceability.

Do not create only a landing page, static dashboard, or frontend prototype. Build a functional end-to-end application with a real backend, machine-learning pipeline, explainability, database integration, audit trail, testing, and deployment configuration.

Work incrementally, inspect the existing repository before making changes, and ensure that every implemented feature works.

## 2. Product Vision

VeriTrace-X helps users identify suspicious supply-chain transactions, understand why an order was flagged, investigate potential fraud, and verify the integrity of its audit history.

The product combines:

- Machine learning for fraud-risk prediction.
- Explainable AI using SHAP and LIME.
- Blockchain-based, tamper-evident audit records.
- Interactive analytics and transaction investigation.
- Human review and decision tracking.

The primary principle is:

**Complex technology. Simple experience.**

A user without any knowledge of AI or blockchain must be able to upload data, analyze transactions, understand risk alerts, review suspicious orders, and verify audit records without needing technical assistance.

## 3. Research Alignment

Build the application around the research concept:

“An Explainable AI Framework for Blockchain-Based Fraud Detection in Supply Chain Traceability.”

Use the DataCo Smart Supply Chain dataset when available, including the research dataset's approximately 180,519 order-line records and the report's approximately 2.25% suspected-fraud figure as research context, not as guaranteed model performance.

Preserve the distinction between suspected fraud, model predictions, and confirmed fraud.

The system must not claim that the model has been validated in production unless actual evaluation results support that claim.

Implement a reproducible training and evaluation pipeline. Compare suitable algorithms, such as Logistic Regression, Random Forest, and XGBoost where appropriate. Select the final model based on measured validation performance, data leakage checks, class imbalance handling, and suitable fraud-detection metrics.

Evaluate precision, recall, F1-score, confusion matrix, ROC-AUC, and PR-AUC where applicable. Clearly document the evaluation methodology and limitations.

## 5. UI/UX Design System

Create a distinctive, polished, award-quality SaaS interface.

The design should be clean, elegant, intuitive, responsive, and visually memorable. Take inspiration from premium enterprise dashboards and modern product websites without copying any specific website.

### Color palette: Clean Amber Intelligence

Use this palette consistently:

- Main background: `#FFFBF5`
- Card background: `#FFFFFF`
- Light amber surface: `#FEF3C7`
- Soft gold: `#FCD34D`
- Primary amber: `#F59E0B`
- Deep amber: `#D97706`
- Dark brown: `#92400E`
- Primary text: `#1F2937`
- Secondary text: `#64748B`
- Border: `#E7E5E4`
- Success: `#059669`
- Critical risk: `#DC2626`

Do not use blue as a primary, accent, gradient, navigation, or button color. Use amber and its shades as the product's primary visual identity.

Green and red may be used for meaningful success and critical-risk statuses. Maintain sufficient contrast and never rely on color alone to communicate risk.

### Typography and layout

- Use Inter or another appropriately licensed, readable sans-serif font.
- Use consistent spacing and a clear visual hierarchy.
- Use approximately 12–16px card corner radii.
- Use subtle borders and shadows instead of excessive glassmorphism.
- Keep the sidebar compact and navigation labels understandable.
- Make tables readable and responsive.
- Use concise headings, descriptive labels, and clear calls to action.
- Avoid unnecessary gradients, decorative charts, oversized cards, and excessive whitespace.

### Animations

Use Motion for React for:
- Page transitions.
- Modal and drawer transitions.
- Card entrances.
- Tab transitions.
- Notifications and tooltips.
- Subtle hover and focus feedback.

Use GSAP for:
- Landing-page hero animations.
- Scroll-triggered storytelling.
- Supply-chain journey animations.
- Carefully designed SVG blockchain visualizations.

Do not let multiple animation libraries control the same element. Keep animations subtle, purposeful, and performant. Support reduced-motion preferences and avoid delaying important user actions.

### Open-source graphics

Use Lucide icons, custom SVG diagrams, and appropriately licensed free illustrations.

Keep most dashboard visuals functional rather than decorative. Prefer actual transaction analytics, shipment timelines, explainability charts, and blockchain verification diagrams.

### E. Transaction Details and Investigation

Design a particularly polished, easy-to-understand transaction details page.

Use order `VX-1024` as an illustrative UI example only. Do not claim its risk score or findings are real unless they are generated from actual model output.

Display:

1. Order summary.
2. Supplier and shipment information.
3. Risk score and risk category.
4. A plain-English explanation of why the model flagged the order.
5. Important factors that influenced the prediction.
6. SHAP-based feature contributions when available.
7. Optional LIME explanation when appropriate.
8. Relevant transaction data.
9. Shipment timeline.
10. Blockchain audit information when the integration is active.
11. Review history.
12. Human review controls.

Use an explanation structure such as:

“Why was this order flagged?”

- The order value is unusually high compared with comparable orders.
- The supplier has limited historical transaction data.
- Some product details do not match the expected pattern.

These must be example explanations, not hardcoded factual findings. In the real application, generate explanations from actual data and model output. If a factor is unavailable, omit it or clearly label it as unavailable.

For the risk score:
- Display the actual model output.
- Explain what the score represents.
- Do not call an uncalibrated model probability a confirmed probability of fraud.
- Show an unavailable state if prediction fails.
- Distinguish model confidence from fraud risk.

Use a visual risk indicator, but make the number, label, and explanation readable without relying on color.

## 7. Machine-Learning Pipeline

Implement a complete reproducible ML workflow.

1. Inspect and document the dataset schema.
2. Identify the target label and confirm its meaning.
3. Validate and preprocess data.
4. Handle missing values and duplicates appropriately.
5. Prevent data leakage.
6. Split data into training and evaluation sets using a suitable strategy.
7. Handle class imbalance using justified techniques.
8. Train and compare candidate models.
9. Evaluate the models using appropriate metrics.
10. Select the model based on measured performance and the intended operational use.
11. Save the trained model and preprocessing pipeline.
12. Expose a prediction API.
13. Generate SHAP and LIME explanations.
14. Record model version, prediction timestamp, and relevant evaluation information.

Do not assume that a dataset column represents confirmed fraud without inspecting its definition.

Do not promise a specific accuracy level before measuring it.

Use a versioned, reproducible training process. Avoid retraining the model for every API request.
